# Issue pipeline

The issue pipeline turns GitHub issues into merged pull requests: a pi-subagents workflow that triages each issue, opens a PR, writes a spec, implements, reviews, fixes, verifies and merges. See the wiki's [Issue pipeline](https://github.com/axolotl-logic/project-buddy/wiki/Issue-Pipeline) page for its goal, rules and design, [Running the issue pipeline](https://github.com/axolotl-logic/project-buddy/wiki/Running-the-Issue-Pipeline) for the operating manual, and [Agent labels](https://github.com/axolotl-logic/project-buddy/wiki/Agent-Labels) for its labels.

## Files

| Path | What it is |
|---|---|
| `src/workflow.js` | The sweep's body: it starts the sweep's driver and awaits each batch of launches the driver asks for, chained one after another; the build ends it by returning the driver's summary. Runs in the pi-subagents sandbox and uses no model tokens itself. |
| `src/workflow/` | The sweep, as strict TypeScript. `sweep.ts` is its driver, `startSweep`: it owns the sweep's state and runs the sweep op, the claim (`stages/entry.ts`), the stage groups (`sweep-stages.ts`), closing parents, the release and the summary, and returns each next batch of launches for `workflow.js` to await. `stages/` holds the stages on the step machine: each is a sync `next` that takes the issue's JSON-safe state and its last launches' results and returns its next launches or `done`, run through the stage dispatch (`stages/index.ts`) in four groups: triage, spec, implement and open-pr; review and the fix rounds; sync and checks; accept, security, merge and publish. The last two groups run once more when merge finds the branch behind its base, so it rebases and merges in the same sweep (#205). With a wiki, merge first rebases the issue's wiki commits onto the wiki's latest version and runs `wiki-check`; publish puts them on the wiki after the code merged, and the conflict resolver (`sync-conflict.ts`, with `conflict-target.ts` for what differs between a code and a wiki rebase) settles a conflict in either (#216). Each change's flows, code and wiki, decide its PR and checks (#217): `flows.ts` works them out, `stages/flow-step.ts` saves them and closes, reopens or stops, `stages/checks-round.ts` runs `wiki-check` before verify and CI, and a wiki-only change ends with the `finish-wiki` op. `launches.ts` builds the launch specs and `launch-results.ts` reads their results, adding each session's spent tokens to the issue's `reportedTokens`, a logged figure that stops nothing (`rate-tokens.ts`: input, output and cache writes, not cache reads, as the orchestrator's optional hourly limit counts them); `sweep-config.ts` reads the run's args and holds the default role context budgets, models and spawn cap and the stage facts. `budget.ts` caps each role's context budget by `sessionTokenCap`; it bounds one session's context, never the issue's spend (budgets-bound-context): nothing charges an issue for its sessions, and its loops end at their round limits (`maxFixRounds`, `maxCiFixes`, `maxSyncs`, `maxConflictFixes`, `maxTriages`, `maxContinuations`). A session that fails on a model provider's rate limit or overload (HTTP 429 or 529, `rate_limit_error`, `overloaded_error` or "cooling down") defers its issue as a network error does (`stages/rate-limit.ts`, `rate-limit-defers`): no stop, and the sweep puts back the round limits' counts the stage began with. Writer prompts tell the session to commit small, working steps often (`commitOftenRule` in `prompts.ts`), and no prompt shows a context budget. `batches.ts` chains the driver's batches with a promise chain, since pi-subagents rejects nested async functions, and `index.ts` exports the one `helpers` object `workflow.js` reads the driver and `driveBatches` from. |
| `src/ops.ts` | The ops CLI's entry: the only code that runs `git` and `gh` or reads tokens, called through the `issue-pipeline-ops` agent. It parses the request's envelope and dispatches each op; its helpers live in `src/*.ts`. |
| `src/ops/` | The ops in strict TypeScript, one module per op (`sweep`, `claim`, `save-state`, `save-spec` (#280), `ask`, `split`, `stop` (#183); `pr` and `sync` (#184); `verify`, with `fails-before-fix`, and `ci-status` (#185); `merge`, with the order between merges in `merge-order`, and `finish` (#186); `cleanup`, which frees closed issues' worktrees at the end of each sweep (#174); `wiki-check`, which checks the links in an issue's changed wiki pages and that new pages are linked (#215); `publish`, with `wiki-sync` and `finish-wiki-sync`, which rebase an issue's wiki commits onto the wiki's latest version and publish them after the code merges (#216); `usage`, which appends a usage record line to the account's latest usage comment on the issue, posting the next one when it is full (#302)), which `src/ops.ts` imports and registers. Each op parses its own request. |
| `src/start-state.ts`, `src/resume-stage.ts`, `src/restart-spec.ts`, `src/spec-files.ts` | Where a claim restarts an issue (`every-role-resumes`): a lifted stop resumes at the stage that stopped, carrying the saved state with every limit reset, so no finished stage runs again (`resume-stage.ts`); a stage after review stands only on a review of the branch's head, and otherwise goes back to review; a specced issue goes straight to implement, with the earlier session's handoff, never through triage and spec again. A restart past spec checks that the test and stub files the saved spec (or its spec.md) documents, in its Tests section and Files list, are on the branch (`spec-files.ts`): when the spec writer wrote them (`specWritesTests`, which #305's spec writer sets), a missing one stops the issue with `agent:stopped-spec-files`; otherwise they go to the implementer as unfinished work, noted in the issue's log. |
| `src/job.ts`, `src/job/` | The stage job's CLI (#232, #233): one sweep pinned to one issue that begins only one stage, printing its summary as one JSON line; it can be stopped, resumed and steered. `args.ts` reads its arguments. `launch.ts` runs each launch as a child process (`ops.mjs`, or `pi --mode rpc` as the launch's installed agent, `agent-definition.ts`, through `rpc.ts`, which sends the prompt and commands and reads pi's records), `status.ts` keeps the issue's `job.json` (each launch's pid, session, last event, tool failures, usage, context budget (a writer session's only), context size, `peakContext`, `firstContext`, `turns`, `contextStop` and outcome) and reads it for `--resume` and `--steer`, `control.ts` owns the live sessions, the steer socket and the stop on SIGTERM or SIGINT, `context-watch.ts` (#271) holds each writer agent's session (implementer, fixer, CI fixer or conflict resolver, and the spec writer since #335) to the config's `contextLimits` (one steer once its turn context passes `soft`, telling it to finish the edit it is in, commit it building, or for the spec writer commit the tests, stubs and spec draft it has, and write the handoff as the next round's summary; past `hard` it is aborted and its result becomes a `handoff`; any other session is neither steered nor stopped, `wrap-up-at-175k`), `stop-handoff.ts` saves a writer stopped at `hard`: on every stop it commits the session's uncommitted work as a WIP commit when the checkout is on its branch with no rebase, merge, cherry-pick or revert in progress and the commit hooks allow it, then updates the handoff through `stop-handoff-text.ts`, which keeps the session's own handoff with a note on that work, keeps an earlier round's unchanged handoff with the job's `## Stopped session <key>` section below it, and writes the whole handoff (its commits, its uncommitted work and its last text) when there is none, `context-log.ts` appends one line per ended session to the issue's `context.jsonl` (role, stage, model, how it ended, peak, first and last context, turns and usage; `killed` for a session the job's stop ended), `launch-record.ts` folds each RPC record into the launch's `job.json` record, `raw-results.ts` maps the exits and session records to the results `launch-results.ts` reads, `pool.ts` runs each batch up to the spawn cap, `structured-output.ts` is the pi extension that gives a session its terminating `structured_output` tool, `pipeline-commit-tool.ts` (#303) is the pi extension that gives a writer or spec writer session `pipeline_commit`, which commits what `pipeline-commit.ts` plans (refusing flags such as `--amend` and `--no-verify`, paths outside the session's scope, and, before git runs, any path in a checkout the stage only reads; its pathspecs are relative to the job's folder and start with `repo/` or `docs/`, #338) in the code and wiki checkouts and asks the job to push over its control socket (`control-protocol.ts`, served by `commit-push.ts`, recorded in `job.json`'s `pushes`), and `roles.ts` (#249) holds each stage's and session's role (reader, writer or merger), its access to its code and wiki checkouts (`read` or `write`; every stage reads the wiki, and only writer stages write code, #338), the config's `jobRoles`, and the env each `pi` gets: no gh token variables and no `jobRoles.<role>.tokenEnv` variable (#303); only the job and its ops hold a token. `checkout.ts` (#250) gives each job its own folder, `work/<slug>/jobs/issue-N-<stage>`, which holds two clones side by side (#338; the folder names live in `layout.ts`): the code checkout `repo/`, cloned from the bare mirror `work/<slug>/mirror.git`, and, when the repo has a wiki, the wiki checkout `docs/`, cloned from `wiki-mirror.git`, each with a pre-commit hook that refuses commits made outside `pipeline_commit` and the ops; every pi session runs in the folder, and every ops request names `repo/` in its `checkout` field. On exit (`teardown.ts`) it saves what either checkout left uncommitted as a patch, `dropped/<job key>-repo.patch` or `-docs.patch` in the issue's run folder (`dropped-patch.ts`, #369: a header naming the issue, the job key `<stage>-<UTC start>` and the base commit, then git's binary-safe diff of everything uncommitted, ignored files left out, which `git apply --index` restores on that commit; nothing applies one, and they go only with the run folder), then records and drops it (`job.json`'s `lostChanges`, as `repo/…` and `docs/…`, and `droppedPatches`, relative to the run folder), names the patches on stderr (`job.log`) and, when the run stopped, posts one keyed coordinator comment saying they were saved, naming the job key and no local path; `exit-push.ts` runs the `exit-push` op for a writer with unpushed commits, in the code checkout or in a wiki it may write, (recorded as `exit-push`, which the next claim adopts from a state saved at implement, open-pr or fix (#315), as it adopts a `pipeline-commit` push), unpushed wiki commits wait in the wiki mirror's `agent/issue-N`, and the folder is removed. `--print-boundary` prints a stage job's role, checkout (its folder), access to `repo/` and `docs/`, env names and network as one JSON line and starts nothing. See "Stage jobs" in the wiki's Running-the-Issue-Pipeline page. |
| `src/roles/` | The roles the stage job runs on the role runner (`src/job/runner.ts`) in place of the sweep, registered by stage in `registry.ts` (`role-state-machines`); `machine.ts` holds a machine's table and transition and `walk.ts` how a run moves. `triage/` is the triage role, which opens no branch or PR (#334). `spec-writer/` is the spec writer's machine for `--stage spec` (#333, #334): `machine.ts` its table, `locate.ts` where a run starts from the saved state, `task.ts` and `reply.ts` its session's task and reply, `checks.ts` its script checks (the reply check with interface coverage, `coverage.ts`, the spec's publication and the close of an earlier PR), `checks-git.ts` those that run git and the commands (the start heads and what the stage committed since them, which a restart's or a continuation's task names, the commit check `check.ts` at the spec head, the no-work test run, the removal of the spec draft and the handoff once the spec is posted, and the resets of the code and wiki branches to their start heads), `ends.ts` its end states (including the too-large stop when a handoff has no continuation left, #335), and `pr.ts` the draft PR's body. No role imports another's modules. |
| `src/orchestrate.ts`, `src/orchestrator/` | The orchestrator (#234): a long-lived process, `node orchestrate.mjs --config <path> [--once]`, that starts stage jobs as the open issues need them. Each tick (`tick.ts`) reads the queue as the sweep op judges it (`snapshot.ts`, with each live implementation's changed files from its branch on GitHub, `branch-changes.ts`, which only an `implement` whose stub files they include waits on, #390), adds what the jobs spent to the hourly token ledger, `runs/<slug>/orchestrator.json` (`ledger.ts`), which holds starts only when the config sets `tokensPerHour` (null or 0, the default, is no limit), holds every start and restart as `rate-limited` for `rateLimitBackoffMinutes` (5 by default, doubling while it repeats, up to 30) after a job whose issue deferred on a model provider's rate limit (`rate-limit-backoff.ts`, `runs/<slug>/backoff.json`; `rate-limit-defers`), lets the pure scheduler decide (`schedule.ts`, over the snapshot's facts and merge ranking in `queue.ts`, with the stacking rules in `stacking.ts`, #290: an issue that waits on another starts on that one's branch, `--stack-on`, once it reaches checks with no open findings, one level deep, unless that one's branch lacks the merge commit of another prerequisite that merged, which holds it as `stacked-on-behind` (#328, `stack.ts`'s `prereqBehind`); a stacked issue waits at merge while its prerequisite is open, goes back to sync when the prerequisite's head moves or it merges, and is held while it is stopped or closed unmerged), spawns the jobs it chose and logs every decision to `runs/<slug>/orchestrator.log` (`log.ts`), then closes the open split parents whose sub-issues are all closed with at least one merged (`parents.ts`, #378: it reserves them as the sweep `orchestrator` in `runs/<slug>/reservations.json`, skipping one another sweep reserved lately, runs the `close-parent` op's code for each, logs each close as `closed-parent` and escalates a close that fails, which the next tick tries again). Before the scheduler, the watchdog (#235, `watchdog.ts`, pure) restarts dead jobs with `--resume` up to `maxResumes` times, then stops the issue with `agent:stopped-job`, steers, then stops, a silent session's job, and steers a session whose calls of one tool failed `failureStreak` times in a row with the last error; `watchdog-budget.ts` (#281, pure) sends SIGTERM to a job whose writer session's context passed its role's context budget (non-writer sessions record no budget, so have no watchdog max), then stops the issue with `agent:stopped-budget` once it has exited; `escalate.ts` (pure) picks what its rules can't settle (a stop they didn't expect, an acceptance fail or `agent:needs-info`), which `log.ts` writes to `runs/<slug>/escalations.jsonl`; `escalation-agent.ts` (#282), when `escalationAgent` is set, runs that agent once per tick that raised escalations, as a read-only `pi --mode json`, and logs its recommended action for each issue, carrying it out through the watchdog's steer, resume and stop only when `escalationAgentActs` is on; `watchdog-memory.ts` keeps what it remembers between ticks in `runs/<slug>/watchdog.json`. `args.ts` reads its arguments. See "Orchestrator" in the wiki's Running-the-Issue-Pipeline page. |
| `src/report.ts`, `src/report/` | The report CLI (#302): `node report.mjs usage --config <path> [--since <date>] [--role <role>] [--issue <n>]` reads the repo's issue comments in one paged listing and prints the usage report from `report/usage.ts`, which is pure: the account's session records grouped by role, state and model (median, p90 and max by nearest rank), the sessions the config's `usageFlags` flag, and each role's five tools with the most output. The flags only label the report. See "Usage report" in the wiki's Running-the-Issue-Pipeline page. |
| `build.ts` | Builds `src/` into `dist/` with esbuild: the workflow's helpers are bundled into an IIFE placed ahead of the sweep's body, which is transformed alone, keeping its top-level `await`, and given its `return sweep.summary();`, since Biome can't parse a top-level `return`; ops, the stage job, its pi extensions, the orchestrator and the report CLI are each bundled into one Node ES module. |
| `dist/` | The build's output, `workflow.js`, `ops.mjs`, `shell-supervisor.mjs` (which `shell` runs each command through, beside `ops.mjs`), `job.mjs`, `structured-output.mjs`, `pipeline-commit.mjs`, `orchestrate.mjs` and `report.mjs`, which the install copies. Ignored by git and Biome. |
| `agents/` | The five agents: `issue-pipeline-ops` (command runner), `-reader` (read-only), `-specifier` (writes the spec, its failing tests and stubs, and the wiki updates, committing only through `pipeline_commit`, plus web search), `-writer`, and `-escalation` (read-only, the orchestrator's optional escalation agent, #282). The reader, specifier and writer also get `codemode`, which scripts calls to their own tools only, so it grants nothing new. |
| `prompts/` | `/pipeline-start` and `/pipeline-pause`, which start and pause a lane in a pi session. |
| `repos/example.json` | Every field of a per-repo config, such as `contextLimits` (`soft` 175000 and `hard` 225000 tokens; writer prompts state both, `soft` must be below `hard`, `hard` must be below every writer's context budget (`min(roleBudgets[role], sessionTokenCap)` for the implementer, fixer, CI fixer and spec writer, 300000 by default) so the job's stop comes before the watchdog's kill, and the stage job enforces both on writer and spec writer sessions only, #271, #335, `wrap-up-at-175k`) and `maxContinuations` (1), the continuations each writer stage, the spec stage included, may have from a handoff before the issue stops as too large (#269, #335). |
| `install.mjs` | Builds, then installs this folder where pi reads it. |
| `test/` | Tests for `src/ops.ts`, `src/workflow.js`, `build.ts` and `install.mjs`, and the harness that runs the built workflow with scripted replies. |

`build.ts` is strict TypeScript, run by Node's type stripping and checked by `tsc` (`tsconfig.json`, which also covers `src/**/*.ts`). The workflow's helpers in `src/workflow/` and the ops CLI, `src/ops.ts` with its modules in `src/*.ts` and `src/ops/`, are typed too. `install.mjs` and the tests are checked JavaScript, typed with JSDoc and checked by `tsc` through `tsconfig.test.json`, which turns on `checkJs`. Only the sweep's body, `src/workflow.js`, is plain JavaScript outside `tsc`, because `allowJs` is off: the sandbox runs it as an async function body with its own globals, which `biome.jsonc` declares for it, and the build adds its `return`, since Biome can't parse a top-level one. `mise //apps/issue-pipeline:check` typechecks, lints (Biome, with the repo's policy), builds and tests all of it.

`{{ISSUE_PIPELINE_ROOT}}` and `{{PI_CODING_AGENT_DIR}}` in the agents and prompts are filled in by the install.

## Install

The pipeline runs from an installed copy, not from this folder. Run `npm ci` at the repo root first, since the build needs esbuild:

```bash
npm ci                                      # at the repo root
mise //apps/issue-pipeline:install:dry-run  # list what would change
mise //apps/issue-pipeline:install          # install
```

It first builds `src/` into `dist/` (as `mise //apps/issue-pipeline:build` does), and stops with `install: build failed` if the build fails. A dry run writes only `dist/`. Then it copies the generated `dist/workflow.js`, `dist/ops.mjs`, `dist/shell-supervisor.mjs`, `dist/job.mjs`, `dist/structured-output.mjs`, `dist/pipeline-commit.mjs`, `dist/orchestrate.mjs` and `dist/report.mjs`, and `repos/example.json`, to `$ISSUE_PIPELINE_ROOT` (default `~/.pi/agent/issue-pipeline`), the agents to `$PI_CODING_AGENT_DIR/agents/issue-pipeline/` and the prompts to `$PI_CODING_AGENT_DIR/prompts/` (default `~/.pi/agent`). It backs up each file it replaces to `$ISSUE_PIPELINE_ROOT-backups/<timestamp>-install/` and records the commit in `INSTALLED.json`. It refuses a checkout with uncommitted changes in this folder unless given `--allow-dirty`, and refuses to install from the pipeline's own worktrees.

Merging a PR changes nothing that runs: only the operator's install does. That way an agent's PR can't change the code that checks its own work. Install from a checkout of a merged commit, between sweeps or with the lanes paused (`/pipeline-pause`). Every op reads `ops.mjs` fresh, but a schedule keeps the `workflow.js` text it was created with, so recreate the lanes after a change to it.

From #303 on, a stage job's sessions commit only through `pipeline_commit`, and since #334 only the spec, merge and publish stages write the wiki (`STAGE_WIKI_ACCESS` in `src/job/roles.ts`); lanes are unaffected.

Each repo's config, its setup and teardown scripts and its token stay local in `$ISSUE_PIPELINE_ROOT/repos/` and `secrets/` (`per-repo-config-kept-local`), as do `clones/`, `work/` and `runs/`. The install never touches them.

## Tests

```bash
mise //apps/issue-pipeline:check      # typecheck, lint, build, then the tests
mise //apps/issue-pipeline:build      # build src/ into dist/
mise //apps/issue-pipeline:lint       # Biome with the repo's policy (npm run lint)
mise //apps/issue-pipeline:typecheck  # tsc on build.ts and src/**/*.ts, then on install.mjs and every test file (tsconfig.test.json)
```

The `test/workflow-stages-*.test.mjs` scenarios run the built workflow through `test/workflow-harness.mjs` with scripted replies, and assert each stage's promised outcome through `test/stage-outcome-test-kit.mjs`: the summary the workflow returns, the ops requests its GitHub-visible effects and saved state go through, the state saved at release, and which sessions ran. They take no snapshots and pin no launch keys or launch order (`tests-pin-promised-behaviour`), so a change to the workflow's internals needs no test update.
