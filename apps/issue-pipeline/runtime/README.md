# Pipeline-owned native runtime

## Contract and supported launch

All five model-session paths (Author, Developer, Hardening, Integration and final read-only Security) use the same versioned policy: native automatic compaction **enabled**, target **175000** tokens, recent-history setting **30000** tokens. This is native context management, not a spending/token budget. Pi's trigger is strictly `contextTokens > contextWindow - reserveTokens`, evaluated at its native turn/tool boundaries; it is not a hard cap checked at every token. Recent retention follows native message/turn boundaries and is approximate, not an exact token slicing guarantee.

The supported adapter is **native Pi 1.2.0 + trusted installed pi-cliproxyapi 0.4.3**. It launches the existing `pi` executable with:

```text
--mode rpc --print --offline --no-approve --no-extensions
-e builtin:codemode -nc -ns -np --no-themes
--model <configured model> --session <existing pipeline session path>
-e <trusted provider index.ts> …existing pipeline extensions/tools/prompts/schema…
```

Explicit RPC wins over `--print` in Pi 1.2.0. `--print` is necessary specifically because CLIProxy 0.4.3 otherwise treats RPC as interactive and can do startup/background discovery and quota requests. In that provider's existing headless branch it uses only its provisioned discovery cache and does not refresh it. Native `--offline` alone does **not** make provider extensions offline, and neither flag prevents later authorized generation requests. This is a narrowly version-checked launch adapter, not a general CLI compatibility promise. Upgrades require renewed source/protocol review and local proof, not removal of the version check or a fallback.

Each session gets a new private `PI_CODING_AGENT_DIR` beside its existing session JSONL. Only pipeline-generated settings live there; no personal settings, model overrides, models.json, auth.json, packages, extensions, skills, prompt templates or themes are copied. Project settings/trust and resource discovery are disabled. Explicit role extensions and the structured-output/commit extensions are retained; commit tools/scopes and read-only tool ceilings still come from the session authority. The native session JSONL and normal timeout, abort, steer, structured-output, error and usage lifecycles remain in place. A steer arriving before verification is refused; abort and process-group stop remain available. No token watcher, kill/restart, second session, replacement architecture, model/provider/CLI fallback or custom compaction hook implements this policy.

For `openai/gpt-6.1-sol` the expected native window is **272000**, so generated settings are:

```json
{ "compaction": { "enabled": true, "reserveTokens": 97000, "keepRecentTokens": 30000 } }
```

`runtime.modelContextWindows` declares expectations; it does **not** override or register model metadata. The supported provisioned profile is deliberately narrow: **OpenAI builtin registration through a distinct CLIProxy endpoint**, not arbitrary custom providers or direct-native endpoints. Other provider/profile shapes refuse pending separate review, never fall back. A different supported OpenAI model requires its own reviewed `provider/model` entry. Thinking suffixes such as `:high` use that same model entry. Missing expectations or windows at/below 175000 refuse before launch. Changed valid windows derive a different reserve. Never fabricate a models.json, CLIProxy contextWindow override or discovery-cache window just to pass this check. CLIProxy can prefer Pi's built-in catalogue over proxy metadata; review the **actual native selected model**, not only the proxy's advertised window.

Before the first prompt, native RPC must answer the correlated `get_state` with success, the exact configured provider/id/window/endpoint and `autoCompactionEnabled: true`. The generated settings and provisioned provider config/cache files are hashed again at that point. Invalid/missing data, changed settings, model drift or a host-provider fallback closes stdin and fails the launch without a prompt. The `runtime_policy` log record contains verified policy numbers, versions and SHA-256 settings/provider-profile/cache provenance, never native headers or credential values. Native get_state does not expose token settings: their evidence is the isolated generated file, its checked hash and the version-pinned native SettingsManager contract, not a fictitious RPC token-settings API. Compaction adds a summary/retained context to **the same native session**; native raw history stays append-only.

## Declared toolchain, isolated model configuration

`runtime.toolchainEnv` is the supported non-secret toolchain declaration in the operator's repository config. It is a closed map accepting only `PATH`, `MISE_DATA_DIR`, `MISE_STATE_DIR`, `MISE_CACHE_DIR`, `MISE_CONFIG_DIR` and `MISE_GLOBAL_CONFIG_FILE`. For example (replace every path with reviewed service-host locations):

```json
{
  "runtime": {
    "toolchainEnv": {
      "PATH": "/opt/service/mise/shims:/opt/service/mise/bin:/opt/service/pi/bin:/usr/bin:/bin",
      "MISE_DATA_DIR": "/opt/service/mise/data",
      "MISE_STATE_DIR": "/opt/service/mise/state",
      "MISE_CACHE_DIR": "/opt/service/mise/cache",
      "MISE_CONFIG_DIR": "/opt/service/mise/config",
      "MISE_GLOBAL_CONFIG_FILE": "/opt/service/mise/config/config.toml"
    }
  }
}
```

These are **absolute POSIX paths**; PATH is colon-separated with no relative or empty entries. There is no shell/template or `~` expansion. Do not put credentials in this map: it is visible in effective configuration and boundary output. Unknown variables (including HOME, Pi configuration and auth variables) are rejected, not passed through. The default `{}` adds no overrides for installations whose inherited toolchain is already HOME-independent. Declared entries override the already-filtered child environment, never the parent job or deterministic operations. They cannot double as declared model credential names.

For HOME-relative mise shims, explicitly preserve the operator-selected executable search order **and all five mise locations**: installs/data, state (including trust), cache, configuration and global configuration. Use the service operator's real locations, not paths derived from the new runtime HOME. No installation, trust command, activation, dependency download or personal configuration discovery runs during preparation. An absolute real node bin before shims is supported too, but preserving only node is insufficient when npm/mise or checks still need mise's state/configuration. Ensure PATH also selects the intended Pi, npm and mise. This is intentionally one declaration for the native `pi --version --offline` probe, RPC Pi process, and ordinary session tools/check descendants, not a probe-only PATH fix or an undocumented `job-env.json` workaround.

Compare executable selection and versions from the **same checkout and working directory** with operator HOME and runtime HOME; project mise version selection still applies. Provision existing trust state deliberately rather than trusting repositories at launch. Runtime HOME and each session's private generated `PI_CODING_AGENT_DIR` remain isolated; no personal Pi settings, packages, auth.json or resources are imported. npm is not required to use a personal `.npmrc`. This declaration does not alter the separately minimal read-only Git subagent environment.

The native probe still requires Pi **1.2.0** and refuses without RPC launch, prompt or fallback on failure. Its 10-second timeout uses SIGKILL so a shim ignoring SIGTERM cannot prevent the refusal. Its refusal includes the normal exit status (including status 0 for a version mismatch), or explicitly says no normal exit status was available and names the spawn/probe error code, timeout or termination signal. Stderr is redacted using declared credentials and credential-like values already known in the runtime input environment, stripped of terminal escapes/unsafe controls, then limited to **2048 UTF-8 bytes**, without splitting a character. The excerpt carries an explicit truncation marker, or an empty-stderr indication. Raw stderr and child-process Error objects are not attached to the refusal or diagnostic records. This is not universal detection of unknown secrets. The existing separately declared model credential and GitHub/pipeline/role-token/undeclared OpenAI filtering rules are unchanged.

Runtime HOME is **configuration isolation, not an OS, filesystem, network, keyring or credential sandbox**. Preserving toolchain locations intentionally permits access to their operator-owned non-secret configuration; same-user tools retain their existing OS access. Source delivery does not install, activate or deploy this runtime. Installation and provisioning remain operator-owned steps after review.

## Explicit provisioning: existing operator host or a new clean VM

The installer copies the example profile, **not** a live provider, credentials or discovery cache. Missing provisioning fails; it never borrows the operator's personal profile. Do not start a job to discover missing dependencies.

1. Operator authorization and the exact-head combined gate/security review come first. Install the reviewed pipeline from a clean checkout using the existing documented install process. Do not change or run global/personal Pi setup as a side effect of pipeline installation.
2. Explicitly provision the trusted native Pi **1.2.0** executable and its dependencies. Declare the service toolchain with `runtime.toolchainEnv` as above (or retain `{}` only for an already HOME-independent inherited PATH). Check `pi --version --offline`; it must print `1.2.0`. The bounded launch check runs this same executable/version command, with the model child's environment, before RPC. This is a trusted installation/version contract, not cryptographic authentication of an executable or every dependency.
3. Separately install/review **pi-cliproxyapi 0.4.3** and its dependencies in an operator-controlled location, for example `/opt/pipeline/providers/pi-cliproxyapi/`. Set `runtime.providerExtension` to the **absolute** installed `index.ts` path; its adjacent package.json must identify that exact package/version. It is explicitly loaded, not discovered from a personal package list. Do not copy extension code into generated agent directories.
4. Provision a dedicated model-child HOME. `runtime.home: null` means `$ISSUE_PIPELINE_ROOT/runtime/home`; an override must be an absolute path (or `~/…`) different from the job HOME. Create it with private ownership/permissions for the service. Do **not** repoint HOME for the job/ops process: their existing GitHub auth/config remains unchanged.
5. Under that HOME, explicitly provision `.pi/agent/pi-cliproxyapi/config.json` from the installed `runtime/pi-cliproxyapi-config.example.json`. Set the real nonsecret HTTP(S) proxy endpoint, enable `builtinProviders.openai` with a nonempty explicit model whitelist, leave `customProviders` empty and retain `$PIPELINE_MODEL_KEY` as an environment reference. The supported optional `apiOverride` is `openai-responses` or `openai-completions` (or null); refreshIntervalMinutes must be absent/0. Config fields are validated strictly; unsupported shapes refuse rather than invoking generic compatibility behavior. The endpoint host cannot be `api.openai.com`: native get_state has no registration-origin field, so a same-native endpoint cannot distinguish CLIProxy registration from native fallback and is deliberately unsupported. The pipeline rejects literal/command-resolved API keys, nonempty usageKey, URL credentials/query/fragment and contextWindow overrides (including custom provider models). Credentials must not be in tracked configs, prompts or logs. The three layers are intentionally different: `runtime.credentialEnv` contains plain **names** (`PIPELINE_MODEL_KEY`), the plugin config contains **`$PIPELINE_MODEL_KEY`**, and the environment contains the separately supplied opaque credential. CLIProxy 0.4.3 treats bare `PIPELINE_MODEL_KEY` as a literal and does **not** support `${PIPELINE_MODEL_KEY}` in its resolver. It resolves `$NAME` before passing the resulting value to native registration; Pi 1.2.0 then interprets commands/templates again. Consequently the pipeline rejects resolved credential values beginning `!` or containing `$`, rather than accidentally executing/interpolating them. Do not use a native auth.json env-name convention or a shell expansion in place of this plugin config syntax.
6. Provision `.pi/agent/pi-cliproxyapi/discovery-cache.json` **separately from reviewed actual catalogue data**. CLIProxy's format is `{ "savedAt": <number>, "discovery": { "source": "well-known" or "v1-models", "upstreamVersion": <string or null>, "builtinProviders": [...], "customPool": [...], "serverDiscoveryExcludes": [...], "upstreamTotal": <integer> } }`. Builtin entries have `name`, `api`, `models`; each model has `id`, `name`, `reasoning`, positive `contextWindow`/`maxTokens` and numeric input/output/cacheRead/cacheWrite costs. Custom entries also have `api`, `suggestedProvider`, `ownedBy`. The pipeline validates this shape before native startup and requires exactly one cached OpenAI provider containing each selected model. Empty/inapplicable/ambiguous cache or disabled/unlisted/malformed provider registration refuses before even the native version probe; a cache-shaped object or generic ACK is insufficient. No automatic discovery or cache generation runs in a job. A stale but valid cache is not refreshed at launch; the operator owns its provenance/freshness, and native metadata must still match. Do not invent cache windows or copy the rest of a personal agent profile. Provider catalogue provisioning can require separate service access/authorization; it is not a model-generation trial or something this source task performs.
7. Set `runtime.credentialEnv` to the explicit **names** of service-provided model credential variables (default `["PIPELINE_MODEL_KEY"]`); all must be present/nonblank in the model child's already-filtered environment. The provider's `$NAME` must name one of them. Do not designate GitHub or role-token variables: they are removed before runtime preparation and must remain unavailable to model sessions. Pipeline-managed variables (`HOME`, `PI_CODING_AGENT_DIR`, `PI_CODING_AGENT_SESSION_DIR`, `PI_OFFLINE`, `PI_SKIP_VERSION_CHECK`, `PI_TELEMETRY`) also cannot be credential names: the pipeline replaces them, so they cannot supply the separately provisioned opaque value. Undeclared `OPENAI_API_KEY` (Pi 1.2.0's supported OpenAI fallback-auth environment input) is explicitly removed from model children. It can remain only when deliberately named as the proxy credential and referenced by the provisioned profile; the distinct-endpoint/registration checks still apply. This list validates required names; it is **not** an allowlist/filter for every other inherited environment variable or an OS secrets boundary.
8. Explicitly set all three `models` and their matching `runtime.modelContextWindows` in the operator repo config; the example uses OpenAI for each. Set the role network descriptions to the actual proxy/tool hosts if appropriate; they remain descriptive, not enforced. Provision any needed shell/git/npm configuration intentionally in the dedicated HOME. Personal `.gitconfig`, `.npmrc`, proxy settings and credential helpers are no longer implicit dependencies. Do not provision GitHub push credentials/helpers into model HOME; pushes still go through the scoped pipeline_commit path.
9. Record versions/paths, profile/cache provenance and effective configuration **without credential contents**. Preserve the root's config, generated settings directories/session JSONL, signed state and recovery artifacts for later review/rollback. Runtime HOME is operator-owned state; install does not create, overwrite, migrate or delete it.

This is reproducible **configuration isolation**, not filesystem, network, keyring or OS security sandboxing. Trusted extensions and model tools still execute with the service user's OS access. It does not solve the separately documented external GitHub authority races. Their documented limitations are unchanged.

This issue does not gate unrelated delivery or select another issue. Credential rotation is not performed or added to an initial queue.

The caller-owned flow and two-account boundary are unchanged: Author → Developer → writable Hardening → caller-serialized Integration → exact-head approval and deterministic merge → actual-result checks → fresh read-only Security → exact security clearance → wiki publication/completion. Rejection preserves already-merged truth and blocks publication/completion. Restart retains authority and own-merge receipts and does not repeat a recorded merge. hippy/lawd are this operator's configured development/review identities, not reusable pipeline constants.

The reusable design and shared-session contract are also recorded in the wiki: Decisions, Reimagined-Pipeline and Pipeline-Job-Contract. Source and wiki delivery do not claim installation or activation.

A source-side effective-config read is distinct from either a job or `--print-boundary`. From the reviewed repo root, with an explicitly selected operator config path:

```bash
node --input-type=module - /absolute/operator/repo.json <<'JS'
```

This reads/parses local config and prints expectations/names/paths only. It does not read token files, contact GitHub/provider, load provider code, validate catalogue freshness, create a job, pin wiki prompts or prove a native runtime has successfully launched. Check profile/cache existence/schema and package provenance separately during provisioning, without printing credentials. Actual runtime verification is still fail-closed on the first subsequently authorized session. Never substitute a fake generic get_state ACK for that evidence.

## Source/API evidence (pinned versions)

Paths below are relative to the corresponding installed package, read-only evidence rather than a reliance on a particular host's installation path:

- Pi **1.2.0** `dist/main.js`: `resolveMode` (explicit RPC before print, lines 81–89), agentDir/bootstrap settings (468), project trust/runtime settings (595–600), CLI resource-loader flags. `dist/config.js` resolves `PI_CODING_AGENT_DIR`; `docs/settings.md` and `dist/core/settings-manager.js` describe native settings. `getCompactionTokenSetting`/`getCompactionSettings` (632–660) resolve exact model overrides ahead of ordinary settings, which is why merging an ambient profile is unsafe.
- Pi `dist/core/compaction/compaction.js`: `shouldCompact` (173–176), `findCutPoint`/projected retained boundary (334–349, 552–625); `dist/core/agent-session.js` `_checkCompaction`, `_runAutoCompaction` and appendCompaction/replaceMessages (2361–2627) implement native continuation rather than a pipeline restart. `dist/core/session-manager.js` and `docs/session-format.md` define append-only entries and context projection. The threshold is strict `>` and retention is approximate.
- Pi `dist/modes/rpc/rpc-mode.js` `get_state` (345–356) returns the actual native `model` object and enabled compaction, **not** reserve/retention settings. `docs/rpc.md` defines lifecycle/commands. `SettingsManager.applyOverrides()` exists in the SDK but is not exposed through ExtensionContext; no supported CLI/RPC token-settings setter justifies an extension-mutation shortcut. The existing CLI/RPC is retained instead of replacing it with an SDK runner.
- CLIProxy **0.4.3** `index.ts` `isHeadlessRun` (59–66) and initialization (224–308): `--print` selects cached registration, bypasses discovery/revalidation and background refresh; quota callbacks return without UI. `src/config.ts` CONFIG_DIR (49) hardcodes `homedir()/.pi/agent/pi-cliproxyapi`, so agentDir isolation alone is insufficient; `resolveConfigValue` (231 onward) resolves `$NAME`, not a bare name or `${NAME}`. Native `dist/core/resolve-config-value.js` (119–136, 192–217) treats bare names as literals and resolves `$NAME`/`${NAME}` templates or leading-`!` commands; the opaque credential is therefore checked before this second interpretation. `src/cache.ts` defines discovery-cache persistence; `src/apply.ts` (40–190) registers builtin models from Pi's catalogue/proxy metadata and applies configured overrides, which this profile forbids for windows. `src/compat.ts` defines endpoint/API normalization.
